# GAUSS batch 001–200 — controlled implementation milestone

This is a **batch delivery target**, not a claim that 200 scientific operators exist today. Only genuinely executable, registered, individually falsifiable operators are counted. Existing operators on `main` are retained; a draft branch is not an integrated or certified delivery.

## Definition of done for the 200-operator milestone

The milestone is NOT complete unless all of the following are true on one exact Git commit:

1. The executable registry has **exactly 200 unique operator IDs** across the eight GAUSS domains, with a real implementation for every ID and no aliases or arbitrary parameter presets counted as new algorithms.
2. The deterministic foundation fixture executes **every registered ID exactly once** and fails closed on any missing, duplicated, unsupported, or skipped operator.
3. Every newly added operator has documented mathematical semantics, numerical/size bounds, deterministic test inputs and output, an independent oracle or mathematical invariant, and invalid-input tests. An expensive exact solver must reject oversized instances rather than claim a partial answer is optimal. Numerical approximations must report residuals or independent reconstruction checks and reject nonfinite results; solving an ill-conditioned system is not a promise of exact real arithmetic.
4. All registered outputs pass GAUSS SHA-256 evidence checks and independent WALLE replay. Negative tests must forge outputs **and recompute all altered hashes**, then prove WALLE rejects them.
5. The existing Quantum participation policy remains enforced: no missing contributor bypass, no reused Ising receipt, and `hardwareExecution=false` for the internal simulator. No quantum advantage or 100% real-world effectiveness is inferred.
6. All applicable GitHub Actions workflows and deployment checks pass on the **same final SHA**; the published evidence artifact is downloaded and checked independently, the patch contains only declared GAUSS-related files, and `main` has not diverged unexpectedly.
7. No new external API, database, queue, service, secret, package dependency, customer mutation, or production activation is introduced by this milestone.

## Real work in the draft batch

Eight bounded graph computations are connected to the GAUSS registry and self-test: nonnegative shortest path with path witness, minimum spanning forest, integer max-flow/min-cut with equality witness, strongly connected components, bipartite maximum matching, DAG critical-path scheduling, exact bounded directed traveling-salesperson tour, and stationary PageRank. Their tests compare separate Bellman–Ford, exhaustive spanning-forest enumeration, exhaustive min-cut enumeration, transitive-closure components, exhaustive matching, recursive DAG critical path, permutation TSP, and independent stationary linear equations.

Nine statistical computations have separate bounded implementations and seeded oracle tests: weighted least-squares line, PAV isotonic regression, Benjamini-Hochberg correction, exact paired sign permutation, Fisher two-sided test, Kaplan–Meier survival, Theil–Sen regression, split-conformal interval and sequential Bernoulli likelihood test.

Seven bounded numerical methods are separately implemented and registered: Gaussian solve, signed log determinant, Cholesky, conjugate gradient, Householder QR, QR least squares and radix-two FFT. Local tests compare independent Cramer/permutation determinants, Cholesky and QR reconstructions, conjugate gradients against a direct linear solve, QR least squares against separately constructed normal equations, and FFT against a direct DFT with round-trip checks. Each operator also rejects invalid inputs, and the connected WALLE test attempts forged, rehashed outputs for every new ID. Standalone testing is not proof of the final SHA's connected execution.

**Progress accounting:** a draft registration is not a merge; the merged count is obtained only from the audited registry in `main`. The target 200 is not to be reported as achieved until its complete acceptance criteria are met. These algorithms solve supplied abstract inputs, not live customs routes, customer performance, or real-world delivery guarantees.
