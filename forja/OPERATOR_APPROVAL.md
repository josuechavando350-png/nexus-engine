# FORJA operator review: offline Ed25519 gate

This module **does not deploy, promote, mutate a job, or create a production service**. It verifies a human's signature over one local, independently inspected, successful four-step FORJA job, its exact Git SHA, the current bytes of its job record and four reports, its nonce, and a 1–15 minute validity window. The result is `APPROVED_FOR_MANUAL_REVIEW_ONLY`, **not** a release authorization usable without further policy and one-time redemption controls.

## Operator procedure

Keep the private Ed25519 key off the checkout and off CI. Provision the trusted public key through an operator-controlled file outside the repository, not by accepting a public key from the signed envelope. Secure access to the local state directory (mode 0700) and verify the Git checkout is clean at the recorded SHA.

1. For an already successful job, generate a short-lived challenge: `node forja/operator-approval.mjs challenge "$PWD" "$STATE_DIR" "$JOB_ID" > /private/challenge.json`.
2. On a separately controlled operator environment, inspect the challenge and its source/evidence identity, then sign it with your private Ed25519 key using the exported `signApproval(challenge, operatorId, privateKeyPem)` function; save the returned JSON as `/private/signed.json`. A key generated by the CI test is **never** a production operator identity.
3. Provision `/private/trusted.json` as `{"operators":{"operator-name":"-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n"}}`, from your trusted key inventory. Run `node forja/operator-approval.mjs verify "$PWD" "$STATE_DIR" "$JOB_ID" /private/signed.json /private/trusted.json`. The command re-inspects the complete job and source bytes before accepting the signature.

The verifier fails closed for an untrusted or changed operator, mismatched job/SHA/evidence, malformed envelope, expired or not-yet-valid window, non-Ed25519 key, or changed/missing report bytes. It never returns stored raw evidence over HTTP.

**Trust limitations:** the state store and trusted-keys file remain local mutable files. A privileged local attacker can manipulate them; there is no external append-only log, hardware-backed trust, host attestation, nonce redemption registry, remote TLS service, deployment adapter, or verified disaster recovery. An accepted signature can be presented again until expiration. Treat this as a bounded offline review primitive, not production release certification.
